用 HTML 写桌面 UI
为 AI agent 定制的 HTML 原生渲染引擎

html-native（引擎核心 Neb = NO-WEB）—— 一个不含浏览器内核（NO-WEB）的 HTML 原生渲染引擎框架。
HTML 是 AI 最会写的 UI 语言；Neb 让它直接渲染成桌面原生窗，
不借 WebView、不打包浏览器内核，也不需要重新编译。

01 — 项 目 背 景

HTML 是 AI 最会写的 UI 语言，但它只活在浏览器里

今天 agent 生成 UI 的事实标准是"吐一张网页"。HTML 本身没有问题——它是模型训练语料里最密集、AI 表达最流畅的界面语言；问题在于，想让它落到桌面上，现有三条路都走不通。

浏览器标签

HTML 的原生归宿只有标签页，没有窗口语义：悬浮层级、点击穿透、秒开秒毁、位置记忆，全都无从谈起。

WebView / Electron

想搬进桌面就得背一份浏览器内核，数千万行、运行时百兆起步；与"agent 高频生成、用完即弃"的形态天然冲突。

原生 UI 框架

SwiftUI、Flutter 都做得了桌面 UI，但编译链重、产物大，改一行就要重新构建——做不到增量与秒级热更新。

html-native 的回答：自研 C99 渲染引擎 Neb（NO-WEB）——agent 写 HTML/CSS，引擎直接渲染成桌面级原生窗。不借浏览器内核，不需要编译，轻量、秒开、可增量热更新：推一份新 HTML，窗口还在原处，内容已经换过一轮。渲染口径由 30 个探针、1145+ 项断言钉死，每轮回归逐值对账——agent 的产物第一次有了机器可验证的桌面出口。

agent 生成 HTML/CSS→ Neb 解析 · 级联 · 布局→ 显示列表（14 种指令）→ 桌面原生窗

上一代方案比的是"能不能画出来"，Neb 比的是"画完之后能不能被机器验证、能不能随时改"。这是 agent 场景真正的门槛。

02 — 技 术 架 构

一个引擎核心，三后端 · 全抽象 · 零 SDK

三层架构：Neb 引擎核心（解析 / 级联 / 布局 / 绘制指令）→ rt 运行时（QuickJS · 媒体宿主 · GPU 宿主 · 定时器与事件）→ platform 平台胶水（每平台一个 hnp_*.c，运行期 dlopen 系统 API，编译期零 SDK 依赖）。平台只出实现，契约全在 hn_platform.h。

关键机制说明
三后端同源同一份显示列表，hnsoft（纯 C 软件光栅）/ cairo / Metal v1（GPU 原语表）三个执行器；覆盖不了的指令整帧静默回退，像素永远正确
探针锚定渲染30 个探针、1145+ 项断言把渲染口径钉成机器可验证契约（颜色 / 几何 / 像素采样 / 跨架构确定性）；性能优化不许改变任何像素
跨架构确定性-ffp-contract=off 关掉 FMA 融合，构建脚本带跨架构逐字节比对门禁；同一文档在不同架构上布局输出逐位一致
零依赖 · 零 SDK引擎与工具纯 C99；AppKit / X11 / Metal / AVFoundation 全部运行期 dlopen；构建与验证链只有 C99 + bash
显示列表14 种绘制指令（HN_CMD_* 枚举，RECT 至 TRIS）：3D 投影四边形、矢量多边形、网格变形、媒体位图、局部清空等，后端可互换
可控网络层hx-get/hx-post 与 QuickJS hn.fetch 走运行期绑定的系统 transport（macOS / Linux 用 libcurl，Windows 用 WinHTTP）；默认拒绝，需 HN_FETCH_ALLOW 白名单放行，重定向逐跳重校验，带超时与响应体上限
本地系统桥sys:// 路由（cpu / memory / disk / battery / clipboard / notify / open / 本地 KV）单点实现，daemon 与 runtime 各自命名空间——不联网即可完成大部分桌面信息展示

依赖边界（如实说明）：渲染与布局为 C99 自研；两处引入外部库而非自研——canvas 2D 的可移植绘制用 canvas_ity（ISC，C++ 单头，vendored），3D 可选后端用 wgpu（Rust, MIT）。二者均为可裁剪的可选依赖，不参与默认构建路径。

03 — 引 擎 内 建 约 定

一行 hn-theme：只写结构，观感由引擎保证

这里解决的是一个 agent 特有的矛盾：模型擅长写结构，不擅长写样式细节。让它每次都从零写一套 CSS，既不稳定也不经济。Neb 的做法是把与渲染强相关的两类决策下沉到引擎层。

设计令牌基底（hn-theme）

一行 hn-theme="dark" 即得完整设计系统：色彩令牌、字阶与行距、卡片 / 按钮 / 输入 / 骨架、投影与 hover 反馈。AI 不写一行 CSS 也能产出精致界面，作者 CSS 排在其后可任意覆盖。

交互容错层（hx-auto）

携带 hx-* 却漏写 id 的元素，装载时由引擎自动补 hx-auto-N——点击、轮询、加载的目标定位不会因生成疏漏而静默失效。这是 agent 生成代码的容错层。

可覆盖，不锁死

引擎给的只是默认值：作者样式排在其后、可任意覆盖；改写 hn-theme 声明即重装令牌基座，窗口与状态不动。组件预设（ui-kit）是 examples/ 层的雏形，按引擎"不含上层 UI/UX"的边界，不在引擎内。

效果：agent 只需产出"要展示什么"，不必产出"该怎么好看"。同一份裸 HTML（无 CSS）在引擎里直接得到配色统一、层级清晰、反馈完整的界面。

裸 HTML（仅结构 + 一行主题声明）→ 引擎内建主题基座→ 精致且一致的桌面界面

04 — 形 态 与 场 景

同一套引擎，长出多种桌面形态

桌宠、数字人、数据大屏、流式会话不是四个独立产品，而是同一套引擎能力在不同声明下的形态：换一组 meta 声明，同一个渲染管线就换一种存在方式。

形态说明
桌宠无边框 + 逐像素透明 + 鼠标穿透 + 悬浮层级 + 位置记忆；画面之外就是真实桌面，观感是"桌面住着一个小东西"而非"开了一个窗口"
数据大屏markdown / JSON / CSV 直染 + Canvas 2D 图表 + sys:// 本地系统桥（CPU / 内存 / 磁盘等信息卡）；一条命令开窗，流式 update 持续推送
数字人网格变形原语（Live2D 同源技术）；官方 moc3 模型由 Cubism Core 绑定承担，motion 数据可驱动自有 rig（呼吸 / 摆动 / 口型 / 视线跟随）
流式会话agent 逐句推送，hn-stream 自动跟随底部（上翻即让出跟随，回到底部自动恢复）；环形缓冲让无限追加的内容在内存与视觉上都收敛
常驻小组件轻应用槽位 + 几何记忆（拖到哪回哪）+ 常驻自启 + 点击穿透"幽灵模式"

交互闭环：输入事件 → 命中链冒泡 → hx-* 触发 → 局部更新 → 重绘上屏；另有宿主协议（Unix socket，JSON-lines）让任意语言的客户端都能 open / update / event / shot / dump，无头模式下不触 GUI 即可完成渲染与取证。

05 — 创 新 点

四个结构性创新

① 无内核的桌面渲染管线

解析到像素一条自有 C99 管线（Neb = NO-WEB）：无 WebView、无浏览器内核、无 Skia；系统 API 全部运行期 dlopen，编译期零 SDK，交叉产物即拷即用。

② 渲染结果可被机器验证

30 个探针、1145+ 断言把渲染口径钉成契约，跨架构逐位对账；无头渲染出 PNG，CI 可做视觉回归。对 agent 而言，这是"生成物可自检"的翻译层。

③ 为 agent 兜底的引擎内建约定

一行 hn-theme 即得整套设计令牌，漏写 id 的 hx-* 元素由引擎自动补位：模型只需产出结构与意图，观感与容错由引擎兜底——把"AI 写 UI"从能用推向可靠。

④ 轻量与热更新

单二进制约 1.4MB，秒开秒毁；推新 HTML 即热更新，窗口与状态不动。相较需重新编译的原生方案，这是 agent 高频迭代场景的关键差异。

06 — 开 源 治 理 与 长 期 发 展

生而开源：单仓库 · 全探针 · 依赖清晰

项目以 MIT 协议在 GitHub 公开迭代，引擎、运行时、平台层、构建与验证链同仓同源；每轮能力落地都以探针断言收口，回归全绿才合入。

依赖 / 组件许可与处理方式
引擎核心 / 运行时 / 平台层自研，MIT，纯 C99（可选后端含少量 C++ 与 Rust）
canvas_ity（canvas 2D 可移植绘制）ISC · C++ 单头 · vendored 于 vendor/canvas_ity
wgpu（neb3-wgpu 3D 可选后端）MIT · Rust · 依赖 wgpu 30 + glam，可选、可裁剪
wasm3（纯计算 WASM）MIT · vendored
PainterEngine（软件渲染实验）MIT · vendored
Live2D Cubism Core（moc3 专有格式）Live2D Proprietary · 二进制与头文件不入仓，由 tools/fetch-cubism-core.sh 由使用方自行获取；未启用时该能力落占位卡，不影响其余功能

长期发展：当前专注 macOS（行为级验证完整），Linux 与 Windows 已完成编译级与符号级对账，待真机验证后推进；路线为三条线——渲染线（GPU 直呈、增量布局）、形态线（数字人完善、多窗协调）、生态线（组件模型、状态与路由、hn dev 脚手架）。

最终目标 —— Smart UX（智能交互）：让 agent 与桌面的交互本身变得智能，而不只是"把界面画出来"。届时每个状态变化都有物理感的过渡、列表增删有交错、对话流逐条滑入；UI 是"真的画出来的"，不是 DOM 翻页。这是方向而非现状：引擎目前的呈现仍缺少成体系的动效语言，该目标登记在仓库 docs/roadmap.md §9.3，属 v0.4 规划（约 12 周），当前尚未达成。

一点思考：agent 时代的 UI 引擎，价值不只在于"渲染得出来"，而在于渲染结果可被机器验证，以及改起来足够轻。前者让 agent 能自检，后者让 agent 敢高频迭代。
